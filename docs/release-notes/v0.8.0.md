# v0.8.0 — Fully local AI on Windows

**Windows PCs now run the entire ATC pipeline on your own machine.** Speech
recognition, intent understanding and the German controller voice — all of it,
locally. No cloud service, no API key, no account, no per-word billing,
nothing leaving your computer. The same self-contained experience Apple
Silicon Macs have had since day one is now available on Windows x64.

This is the headline of the release, and it closes the last real gap between
the two platforms.

| | macOS (Apple Silicon) | **Windows x64** | Intel Mac |
|---|---|---|---|
| Local (no cloud) | ✅ Metal | ✅ **Vulkan — new in 0.8.0** | ❌ |
| OpenAI cloud | ✅ | ✅ | ✅ |
| Mistral cloud | ✅ | ✅ | ✅ |

Switch it on under **Settings → Backend → Local**, then download the models
from the **Models** tab. After that you can fly with the network cable
unplugged.

## What "fully local" actually means here

- **whisper** transcribes your radio calls — on your GPU, via Vulkan.
- **Llama 3.2 3B** resolves the intent when the rule-based parser is unsure —
  same GPU.
- **Piper `de_DE-thorsten`** speaks the controller's replies — on the CPU, and
  it is a genuinely German voice. Neither cloud provider offers one: OpenAI
  has no German voice at all, and Mistral's Voxtral presets are English, so
  German comes out with an American accent. **Local mode is the only way to
  get accent-free German ATC**, and it is now available on Windows too.
- **Nothing is transmitted.** No audio, no transcripts, no position data.
- **No running costs.** No key to manage, no quota, no subscription.

Response times are comparable to Apple Silicon.

### Why Vulkan and not CUDA

`vulkan-1.dll` ships with your graphics driver, so there is no multi-hundred-
megabyte GPU runtime to download, and AMD and Intel GPUs work as well as
NVIDIA. X-Plane 12 already renders through Vulkan on Windows anyway.

The trade: roughly 10–30 % less throughput than CUDA on the same card, and
the models share VRAM with X-Plane's own renderer. Where no Vulkan compute
device is available — as on some virtualised cloud PCs — it falls back to the
CPU rather than failing.

The models (~2 GB) are not bundled. Download them in-sim from the **Models**
tab, exactly as on macOS.

## ⚠️ Before you update

### Windows: check the Visual C++ Redistributable

The plugin itself needs nothing, but the bundled `piper.dll` and
`onnxruntime.dll` require the **Microsoft Visual C++ 2015–2022
Redistributable (x64)**. Most systems already have it — X-Plane 12 and
practically every game installs it — so this rarely bites.

The symptom is worth knowing because it is easy to misread: the plugin loads
normally, the cloud modes work fine, and only the **first ATC voice playback**
fails, with `0xC06D007E` in `Log.txt`. If you see that, install the
redistributable from Microsoft before investigating anything else.

### Upgrading from v0.6.0 or older: one orphaned file

v0.6.1 renamed the plugin folder and the plugin binary from
`xp_wellys_devfr_atc` to `xp_wellys_vfr_atc`. The updater only manages files
it knows about — the same rule that protects your ~2 GB of downloaded models —
so the old binary was never removed, and X-Plane has been loading **both**
copies ever since. If the updater kept reporting a new version while the
plugin's own window showed an older one, this was why.

**Via the SkunkCrafts Updater:** nothing to do. This release removes the
orphan automatically.

**If you install by unzipping manually:** the ZIP unpacks as
`xp_wellys_vfr_atc/`, so it lands *beside* any old `xp_wellys_devfr_atc/`
folder rather than replacing it, and you end up running two plugins. Delete
the old folder:

```
X-Plane 12/Resources/plugins/xp_wellys_devfr_atc/     <- delete this
X-Plane 12/Resources/plugins/xp_wellys_vfr_atc/       <- keep this
```

Your API keys and settings are unaffected — keys live in the OS credential
store. Downloaded models are re-used once the new folder points at them.

Anyone who first installed **v0.6.1 or later** was never affected.

## Fixed

**macOS: speech recognition was degraded by the audio input path.** The
capture layer adopted the microphone's native rate (typically 48 kHz) and
converted to the 16 kHz the recognisers expect using unfiltered linear
decimation. Without a low-pass filter, everything above 8 kHz folds back into
the speech band — and 4–10 kHz is precisely where the sibilants live that
distinguish spelled callsigns. "Foxtrott", "Oscar" and "Sierra" collapsing
into each other was the expected signature.

macOS now asks Core Audio for 16 kHz directly, so the system's own
band-limited converter does the work, and the software fallback (still used by
devices that refuse a 16 kHz format, such as some Bluetooth headsets) is a
proper windowed-sinc converter.

This affected **all three backends on macOS**, not just Local: the conversion
happens before the audio reaches any recogniser, so OpenAI and Mistral
received the same aliased input. Windows was never affected.

Honest caveat: the mechanism is proven and covered by a regression test, but
the actual improvement in recognition accuracy has not yet been measured.

**Windows: the Piper voice crashed on first use.** Two independent bugs that
occurred stacked, so each fix only changed the error code and looked like a
failure. The bundled library declared an ONNX Runtime environment at namespace
scope, whose constructor ran under the Windows loader lock and crashed there;
and the delay-load helper resolved DLLs against a search path that does not
include the plugin's own directory. Both are fixed (`xp_wellys_libs` 0.4.2
plus an explicit preload by absolute path).

A failure in the voice engine now also degrades gracefully with a diagnostic
instead of taking the plugin down.

## Maintenance

Added `make verify-install`, which CRC32-compares an installed tree against
the published update files and names anything stale. The updater records its
version in a config file it writes itself, so it can report a successful
update even when a file replacement did not happen — this makes that visible
instead of leaving it to guesswork.

`make release` now refuses to run unless you are on `main` and up to date with
the remote, so a release tag cannot accidentally be cut from an older tree.
